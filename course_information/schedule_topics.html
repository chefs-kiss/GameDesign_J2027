    Session plans

    Monday, Jan 4 — History of the Game Industry HISTORY

    Morning — What is a game?

    • Warm-up: What is the first game you remember choosing to play rather than being handed? What made you choose it?
    • Industry eras as design constraints: arcade coin-op economics, cartridge limits, shareware/PC, mobile F2P retention, engine-era indies — each business model produces a different shape of game.
    • Fullerton’s definitional elements: players, objectives, procedures, rules, resources, conflict, boundaries, outcome.
    • Stress-testing the definition against edge cases: SimCity, Dwarf Fortress, walking sims, idle games, Twine pieces.
    • Reflection: Which formal element would you remove first before the thing stops being a game? What breaks when you do?

    Afternoon — Game Design Kits Lab

    • Warm-up: With only a deck of cards, dice, and tokens, what is the smallest complete game you can describe in one sentence?
    • In pairs, build a playable game from a design kit in 45 minutes under a hard constraint (e.g. no reading required, one page of rules).
    • Swap kits and play a classmate’s game with the designer silent — no clarifications allowed.
    • Reflection: What did players do that you did not design for? Was it a bug or a feature?

    Tuesday, Jan 5 — Mechanics, Dynamics, Aesthetics MDA

    Morning — The MDA framework

    • Warm-up: Describe a game you love in one sentence without naming a single mechanic.
    • Mechanics → dynamics → aesthetics, and why designers and players travel that chain in opposite directions.
    • The eight aesthetics (sensation, fantasy, narrative, challenge, fellowship, discovery, expression, submission) as a replacement for the word “fun.”
    • Worked example: change one mechanic in a familiar game and trace the dynamic and aesthetic consequences downstream.
    • Reflection: Take yesterday’s kit game — which aesthetic were you actually delivering, as opposed to the one you intended?

    Afternoon — Godot lab 1: the editor and your first scene

    Resource: Godot Tours 101

    • Warm-up: What do you expect a game engine to do for you that you would otherwise have to write yourself?
    • Install Godot 4; run the interactive editor tour; project and file layout.
    • Nodes, scenes, the scene tree, and instancing — the engine’s core mental model.
    • Build a scene in which one sprite responds to keyboard input.
    • Reflection: Name one thing the editor did for you today that you would not have known how to write.

    Wednesday, Jan 6 — Formal Elements of Games ELEMENTS

    Morning — Formal elements & the design doc

    • Warm-up: Rules or objectives — which one, changed slightly, would break your favorite game faster?
    • Each formal element in detail, with an example and a counter-example from a game everyone has played.
    • Reading a game as a system rather than as a story or a genre label.
    • What a design doc is for: a shared, revisable contract about the system — not a sales pitch.
    • Reflection: Which formal element is hardest to see from the outside when you only watch someone else play?

    Afternoon — Design Doc lab: SM3DW, Celeste, A Short Hike, Portal (sound off)

    • Warm-up: Predict what you will lose when the sound goes off. Write it down; we check it at the end.
    • Rotate ~20 minutes per title, sound off, filling in a formal-elements table for each.
    • Compare: which game taught you its rules fastest, and by what means — text, level geometry, animation, failure?
    • Note what became illegible without audio: feedback, threat cues, reward confirmation.
    • Reflection: Which of the four has the tightest fit between its formal elements and its aesthetic goal? Defend it in three sentences.

    Thursday, Jan 7 — The Game Loop GAMELOOP

    Morning — Loops and feedback

    • Warm-up: Draw the action you repeat most often in any game you play. How many seconds does one repetition take?
    • Core loop, session loop, meta loop — three timescales, three different reasons a player returns.
    • Feedback as a chain: input → system response → readable outcome → next decision; what happens when a link is missing.
    • System dynamics (GDW Ch.5): emergence, positive and negative feedback loops, runaway leaders and rubber-banding.
    • Reflection: Of your three loops, which is weakest in the game you would most like to build?

    Afternoon — Godot lab 2: GDScript & signals

    Resources: Learn GDScript From Zero · Signals best practices

    • Warm-up: How would you tell one object that something happened to another, without the two of them knowing about each other?
    • GDScript foundations: variables, functions, conditionals, typed GDScript.
    • Signals as the engine’s event system; connecting in the editor vs. in code.
    • Build a complete micro-loop: collect an item → score updates → visible and audible confirmation.
    • Reflection: Where did your loop feel dead? What single piece of feedback would fix it?

    Friday, Jan 8 — Procedures vs. Rules PROCEDURES

    Morning — Who enforces what

    • Warm-up: Name one rule and one procedure in basketball. Which is easier to enforce in code, and why?
    • Rules constrain the space of legal states; procedures instruct players on how to act within it.
    • Enforcement: the honor system, the referee, and the engine — and how automatic enforcement quietly changes a game’s texture.
    • Translating a rulebook clause into a function: preconditions, effects, edge cases.
    • Reflection: Which rule from your kit-lab game would be impossible (or miserable) to enforce digitally?

    Afternoon — Godot lab 3: your first complete 2D game

    Resource: Your First 2D Game (Godot 4)

    • Warm-up: What is the minimum a game needs before it can have a win state and a lose state?
    • Player scene, enemy scenes, and spawning.
    • A game manager / autoload holding score and state; scene transitions and restart.
    • Ship something playable end-to-end — start screen, play, lose, restart.
    • Reflection: Your game now enforces its own rules. Which rule did the engine let you be lazy about writing down?

    Session plans

    Monday, Jan 11 — Sprite Graphics SPRITES

    Morning — Graphics vs. aesthetics

    • Warm-up: Name a game with dated graphics that still looks good to you. What is doing the work?
    • Fidelity is not style: why art direction outlives hardware, and why “better graphics” is the wrong axis.
    • Readability first — silhouette, contrast, restricted palettes, figure/ground separation under motion.
    • Animation as information: anticipation, key poses, follow-through, and the frames that communicate state.
    • Reflection: Screenshot your Godot project. Can a stranger tell which thing is the player in under a second?

    Afternoon — Godot lab 4: pixel art & animation

    • Warm-up: Why does pixel art usually look blurry or shimmery the first time you import it?
    • Import settings, filtering, snapping, and viewport scaling for crisp 2D.
    • AnimatedSprite2D / AnimationPlayer; driving animation from character state rather than from input.
    • Add idle, run, and jump animations, plus one piece of environmental motion.
    • Reflection: Which animation changed how the game felt rather than how it looked?

    Tuesday, Jan 12 — Physics PHYSICS

    Morning — Game feel vs. simulation

    • Warm-up: Two platformers with identical jump height feel completely different. Name three things that could differ.
    • Why game physics is not physics: acceleration, friction, terminal velocity, asymmetric rise/fall gravity.
    • Forgiveness mechanics — coyote time, jump buffering, variable jump height — and the ethics of lying to the player.
    • Deriving jump parameters from design intent (desired height and distance) instead of guessing numbers.
    • Reflection: Which single number in your project most controls how your game feels?

    Afternoon — Godot lab 5: CharacterBody2D & jump tuning

    • Warm-up: What would you change first to make your character feel heavier?
    • CharacterBody2D, move_and_slide, and frame-rate independence with delta.
    • Exported tuning variables so jump apex, fall speed, and run acceleration can be changed live.
    • Implement coyote time and variable jump height; A/B test with a neighbor.
    • Reflection: Did the more forgiving version feel easier, or just better? What is the difference?

    Wednesday, Jan 13 — Collision Detection HITBOX

    Morning — Hitboxes and frame data

    • Warm-up: In a fighting game, two attacks land on the same frame. Who should win, and how would you decide?
    • Collision shapes: AABB, circle, capsule, polygon — the cost/precision tradeoff.
    • Hitbox vs. hurtbox vs. collision shape: three different jobs, routinely confused.
    • SF2 analysis: startup / active / recovery frames, priority, and why hitboxes rarely match the sprite.
    • Reflection: Sketch the hitbox and hurtbox for one attack in a game you know. Where did you have to guess?

    Afternoon — Godot lab 6: hitboxes, hazards, and i-frames

    • Warm-up: Which of your objects should collide with which? Sketch the matrix before you write anything.
    • The Area2D hit/hurtbox pattern; separating “what I damage” from “what damages me.”
    • Physics layers and masks as a design document in disguise.
    • Add a damaging hazard, a health value, invincibility frames, and hit feedback.
    • Reflection: Where did your collision setup produce a result that was technically correct but felt unfair?

    Thursday, Jan 14 — Game AI AI+PATH

    Morning — Readable behavior

    • Warm-up: Name an enemy whose behavior you can predict perfectly. Is that a design failure?
    • Readable beats smart: the player must be able to build a mental model and act on it.
    • Finite state machines, steering behaviors, and simple patrol/chase/flee architectures.
    • Pathfinding: grids, navigation regions, and A* — and when pathfinding is overkill.
    • Telegraphing, reaction windows, and enemy AI as a difficulty dial.
    • Reflection: What is the smallest set of states your enemy needs in order to be interesting?

    Afternoon — Godot lab 7: enemy AI & pathfinding

    Resources: Navigation2D tilemap pathfinding · Intro to steering behaviors

    • Warm-up: Write your enemy’s states and the exact condition for each transition — before you open Godot.
    • Implement an FSM-driven enemy: patrol, detect, chase, lose interest.
    • Add pathfinding or steering so the enemy handles terrain it was not authored for.
    • Tune detection radius and telegraph duration, then playtest with someone who has not seen it.
    • Reflection: Your tester died. Could they explain why? If not, do you fix the AI or the telegraph?

    Friday, Jan 15 — Physical Prototypes PHYPROT

    Morning — Prototyping & Mini Game Jam launch

    • Warm-up: What can you learn from paper in ten minutes that would take ten hours in Godot?
    • GDW Ch.7–8: a prototype answers one question; it is not a small version of the finished game.
    • The 7-step worldbuilding exercise as a generator of constrained premises.
    • Jam rules: one verifiable design question per prototype, physical materials only, playable by 11:30.
    • Reflection: Write the single question your prototype exists to answer. Tape it to the table.

    Afternoon — Mini Game Jam: playtest physical prototypes

    • Warm-up: What is the one thing you want to see a stranger do with your prototype?
    • Rotate tables every 15 minutes; designers observe silently and take notes.
    • Record what players did, not what they said; timestamp confusion and hesitation.
    • One revision between rounds, then test again with fresh players.
    • Reflection: Which prototype in the room — yours or someone else’s — deserves nine more days of work, and why?

    Session plans

    Monday, Jan 18 — Exam 1 & project kickoff

    Morning — Exam 1

    • Warm-up: Five minutes, closed notes, ungraded: list every formal element you can remember, then compare with a neighbor.
    • Covers Block A: definitions of games, formal elements, MDA, loops and feedback, procedures vs. rules, physics/collision/AI concepts.
    • Format: short answer plus one applied design question (given a mechanic, predict the dynamics).
    • Reflection: Which concept do you still not trust yourself to use? Name it — this is what to ask about this week.

    Afternoon — Team project kickoff (build off the mini prototype jam)

    • Warm-up: Which jam prototype would you want to work on for nine days, and what would you change about it first?
    • Two-minute pitches of surviving jam prototypes, then dot-voting to a shortlist.
    • Scope reality check: nine working days, a team of four, one vertical slice — not a full game.
    • Form provisional teams around the surviving pitches; each team names its one-sentence player fantasy.
    • Reflection: Name one thing your team has already decided not to build.

    Tuesday, Jan 19 — Game Ideas + Worldbuilding WORLD

    Morning — Ideas and worlds

    • Warm-up: The magic circle — name a moment when it broke for you mid-play. What broke it?
    • Ideation techniques (GDW Ch.6): structured brainstorming, constraint-driven generation, the “what if” chain.
    • Dramatic elements (GDW Ch.4): premise, character, and story as pressure on mechanics, not decoration.
    • Worldbuilding that pays rent: every fiction choice should justify or explain a mechanic.
    • Reflection: State your world in one sentence and your core mechanic in one. Do they actually need each other?

    Afternoon — Agile roles, team formation, project structure

    • Warm-up: What is the worst team project you have been part of? What actually caused it?
    • Roles (design lead, tech lead, art/audio, producer), rotating standups, and a working agreement in writing.
    • Project structure: folder and scene conventions, naming, and a .gitignore for Godot; asset and version control workflow.
    • Backlog: epics → tasks → this-week board, plus an explicit definition of done.
    • Reflection: Which role do you least want, and who on your team is covering it?

    Wednesday, Jan 20 — The Quiet Year

    Morning — Worldbuilding by map

    • Warm-up: Name a game world you could describe convincingly without describing its plot.
    • Play The Quiet Year in teams: deck-driven, GM-less, collaboratively drawing a map.
    • The map is the artifact — landmarks, scarcity, contested spaces, and abandoned projects.
    • From board-game worldbuilding to level space: which places on your map want to be walked through?
    • Reflection: Which spot on your map is the most interesting place to stand? What would a player do there?

    Afternoon — Concept → design doc draft

    • Warm-up: What does your player do in the first thirty seconds?
    • Turn the map into a concept: player fantasy, core loop, one page of formal elements.
    • Write the scope cut list — a ranked list of features you will drop, in the order you will drop them.
    • Greybox the vertical slice in Godot with placeholder art; no polish today.
    • Reflection: What is the riskiest assumption in your concept, and how would you test it this week?

    Thursday, Jan 21 — Level Design LEVELS

    Morning — Levels as teaching

    • Warm-up: Describe the first room of a game you know well. What did it teach you, and how?
    • The 4-step structure: introduce, develop, twist, conclude — one mechanic at a time.
    • Doom (Devs Play): sightlines, landmarks, arena shapes, looping non-linear layouts, and reward for exploration.
    • Teaching without text: affordances, safe failure, and the designed first death.
    • Reflection: Sketch how your level teaches your hardest mechanic with no tutorial text at all.

    Afternoon — Workday (Design Doc due)

    • Warm-up: What is the riskiest unknown in your build right now?
    • Finish and submit the design doc, including the scope cut list.
    • Assign vertical-slice tasks against the board; every task has an owner and a day.
    • Instructor check-in with each team: scope, risk, and one thing to cut.
    • Reflection: If you lost one team member tomorrow, what would you cut first?

    Friday, Jan 22 — Level Design: pacing & flow LEVELS

    Morning — Rhythm and iteration

    • Warm-up: Chart the intensity of your favorite level over time. Where is the peak, and what follows it?
    • Pacing and rhythm: tension, release, rest beats, and why unbroken intensity reads as flat.
    • Difficulty curves and the flow channel; gating, critical path vs. optional content, and backtracking.
    • Level iteration in practice: greybox → test → cut; the level you keep is the third one you made.
    • Reflection: Where is the rest beat in your vertical slice? If there isn’t one, where will you put it?

    Afternoon — Physical prototype demos

    • Warm-up: What should we deliberately ignore in your demo today?
    • Each team demos a paper or greybox version of one level to another team.
    • Silent-observation protocol; feedback given only as “I noticed…” and “I wondered…”
    • Teams log every point of confusion with a timestamp.
    • Reflection: What will you change before Monday, and what did you decide to defend?

    Session plans

    Monday, Jan 25 — Game Balancing BALANCE

    Morning — Balance for whom?

    • Warm-up: Name a “broken” option in a game you play. Why do you think it has not been fixed?
    • Two different problems: the single-player difficulty curve vs. multiplayer symmetry and viability.
    • Perfect imbalance: why a permanently shifting metagame can be healthier than a solved one.
    • Dominant strategies, cost curves, and the spreadsheet as a design tool.
    • First moves: opening decisions, information asymmetry, and the paradox of too much choice.
    • Reflection: What is the dominant strategy in your own game right now? (If you don’t know, that’s the answer.)

    Afternoon — Balancing your game

    • Warm-up: Which number in your project has never been changed since the moment you first typed it?
    • Pull tuning constants out of code into exported variables or a resource file.
    • Build a deliberate difficulty pass: forgiving / intended / punishing, and decide which one strangers get at the expo.
    • Test with someone outside your team; record time-to-first-failure and time-to-first-success.
    • Reflection: Did your tester fail for the reason you designed, or a different one?

    Tuesday, Jan 26 — Playtesting TESTING

    Morning — How to run a test

    • Warm-up: What is the difference between “do you like it?” and a question that actually produces usable data?
    • GDW Ch.9: who to test with, when to stop using friends, and the rule against teaching or defending.
    • Kinds of tests: usability, fun, difficulty, balance, accessibility — each needs a different script.
    • SMB 1-1 (watch & play): what the level intends to teach vs. what players actually do in it.
    • What to instrument: deaths by location, time per section, retries, and abandonment.
    • Reflection: Write your team’s test script — three tasks and three questions, nothing more.

    Afternoon — Flex lab

    • Warm-up: Turn your game’s sound off. Now describe what a player loses.
    • Pick one track and ship it today: audio (SFX and music), UI and menus, juice (screenshake, tweens, particles), or accessibility (remappable input, colorblind-safe palettes, readable text).
    • Time-boxed: whatever you choose must be in the build by end of session.
    • Demo the improvement to one other team and get a yes/no on whether it landed.
    • Reflection: Was that polish, or was it a missing piece of feedback you had been ignoring?

    Wednesday, Jan 27 — Legal Issues + ROM Hacking IP

    Morning — What you can and cannot own

    • Warm-up: Is a game mechanic copyrightable? Make a guess and commit to it.
    • Copyright, trademark, and patent in games: code, art, and audio are protected; rules and mechanics largely are not.
    • Clones, parody, and fair use — why legal and advisable are different questions.
    • ROM hacking, emulation, DMCA takedowns, fan projects, and the preservation problem.
    • Asset licenses in practice: CC0 vs. CC-BY vs. “free to use,” and what attribution actually obligates you to do.
    • Reflection: Audit your project: list every asset you did not make and the license it came under.

    Afternoon — Cross-team playtest (working game due)

    • Warm-up: What is the single thing you most need to learn from today’s testers?
    • Submit the working build before testing begins — no last-minute changes.
    • Rotation: each team runs its test script on two other teams, silently observing.
    • Triage the results immediately into must-fix / nice-to-have / won’t-fix, and put must-fix on the board.
    • Reflection: Which piece of feedback do you disagree with, and can you justify overruling it?

    Thursday, Jan 28 — Exam 2 & workday

    Morning — Exam 2

    • Warm-up: In pairs, five minutes: each of you explains one Block B concept to the other without notes.
    • Covers Block B: worldbuilding and dramatic elements, level design and pacing, balancing, playtesting methodology, IP basics.
    • Format: short answer plus an applied question on a level or balance problem.
    • Reflection: Which idea from this course will you still be using in a year?

    Afternoon — Workday: feature freeze

    • Warm-up: Say out loud the feature you are still hoping to sneak in. Now cut it.
    • Must-fix bugs only; the feature list is frozen.
    • Export and run the build on a machine that is not yours — the classic expo-day failure.
    • Prepare expo materials: title card, controls diagram, and a sixty-second pitch.
    • Reflection: What is your rollback plan if the build breaks tomorrow morning?

    Friday, Jan 29 — Game Expo

    Morning — Wrap-up & setup

    • Warm-up: What would you tell yourself on January 4th, knowing what you know now?
    • The through-line: formal elements → prototype → playtest → iterate → ship, and where each stage caught a problem.
    • Postmortem structure: what went right, what went wrong, what we would do differently — with evidence.
    • Set up stations, controls cards, and rehearse the sixty-second pitch.
    • Reflection: Which decision this month improved your game the most, and when did you make it?

    Afternoon — Game Expo (final game due)

    • Warm-up: Who is your ideal player walking into this room today?
    • Rotate in shifts: half the team demos, half plays other teams’ games.
    • Collect visitor feedback cards; watch at least three strangers play without intervening.
    • Submit the final build and the written postmortem by end of day.
    • Reflection: What is the next thing you would build, and which mechanic from this project would you keep?
